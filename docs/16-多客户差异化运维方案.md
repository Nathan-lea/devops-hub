# 多客户差异化运维方案

> **文档编号**：16
> **适用场景**：纳管多个客户的服务器，各客户 SLA 等级、监控阈值、告警渠道、安全基线、备份策略、变更窗口等要求不同，需差异化纳管。

---

## 一、背景与目标

### 1.1 问题描述

本运维系统纳管约 100 台主机，分属**不同客户**。每个客户的需求差异体现在：

| 维度 | 差异化表现 |
|------|-----------|
| SLA 等级 | premium（99.99%）/ standard（99.9%）/ basic（99.5%） |
| 监控阈值 | 核心客户 CPU 告警 90%，普通客户 85% |
| 告警渠道 | 高端客户需电话通知，普通客户仅 IM+邮件 |
| 安全基线 | 金融客户 CIS L2 + 等保三级，普通客户 CIS L1 |
| 备份策略 | premium 30 天保留 + 异地，basic 仅 7 天本地 |
| 变更窗口 | 各客户业务高峰不同，变更窗口与 blackout 期不同 |
| 访问控制 | 部分客户仅限堡垒机访问，部分允许直连 |
| 合规要求 | 等保 / GDPR / PCI-DSS 差异化 |

**核心矛盾**：若用单一扁平配置纳管所有客户，要么过度严格（basic 客户成本浪费），要么过度宽松（premium 客户合规不达标）。

### 1.2 设计目标

1. **一套平台纳管多客户**，避免为每个客户单独部署运维工具栈
2. **配置以客户为维度隔离**，一个客户的配置变更不影响其他客户
3. **默认基线 + 覆盖**，新增客户只需写一个 Profile 文件，80% 配置继承默认值
4. **告警按客户路由**，各客户告警发往各自接收渠道，互不干扰
5. **操作可审计**，所有差异化配置版本化于 Git，变更可追溯

## 二、架构设计

### 2.1 核心思想：默认基线 + 客户 Profile 覆盖

```
                    ┌─────────────────────────┐
                    │   默认基线 (group_vars/all)│  ← 全局默认值
                    │   configs/rules/*.yml     │  ← 全局告警阈值
                    └────────────┬─────────────┘
                                 │ 覆盖
                    ┌────────────▼─────────────┐
                    │  客户 Profile             │  ← 逐客户差异化
                    │  customer-profiles/<id>.yml│
                    └────────────┬─────────────┘
                                 │ 驱动
          ┌──────────┬───────────┼───────────┬──────────┐
          ▼          ▼           ▼           ▼          ▼
     ┌─────────┐┌────────┐┌──────────┐┌─────────┐┌────────┐
     │Inventory ││group_  ││Prometheus││Alert-   ││Ansible │
     │分组      ││vars    ││targets   ││manager  ││Playbook│
     │customer_ ││覆盖    ││+customer ││按customer││按客户  │
     │<id>      ││        ││标签      ││路由     ││限范围  │
     └─────────┘└────────┘└──────────┘└─────────┘└────────┘
```

**关键设计决策**：

| 决策 | 选择 | 理由 |
|------|------|------|
| 配置隔离方式 | Ansible group_vars 目录 | Ansible 原生机制，自动加载，无需自定义代码 |
| 监控差异化 | Prometheus 标签 + 覆盖告警规则 | 标签驱动，告警继承 customer 标签 |
| 告警差异化 | Alertmanager matchers 路由 | 按 customer 标签路由到不同 receiver |
| 安全差异化 | Playbook 条件判断 + group_vars 变量 | 基线等级变量驱动任务跳过/执行 |
| 备份差异化 | group_vars 变量传入备份脚本 | 保留天数/频率/异地开关由变量控制 |

### 2.2 三层 Inventory 分组设计

```
第一层：customer_<id>              驱动 group_vars 差异化（如 customer_acme）
  └─ 第二层：customer_<id>_<role>   驱动 Playbook 任务（如 customer_acme_mysql）

第三层（跨客户聚合）：
  role_<role>                       全局巡检（如 role_mysql = 所有客户的 MySQL）
  <cloud>                           按云厂商（如 aliyun / aws / onprem）
  <distro>                          按发行版（如 debian / ubuntu / centos）
```

**Inventory 文件**：`playbooks/inventory_multi_customer_example.ini`

```ini
# 客户 A 主机
[customer_acme_mysql]
acme-mysql-master ansible_host=10.10.2.10
acme-mysql-slave-01 ansible_host=10.10.2.11

# 客户聚合组
[customer_acme:children]
customer_acme_web
customer_acme_mysql
customer_acme_redis

# 跨客户角色聚合（全局巡检用）
[role_mysql:children]
customer_acme_mysql
customer_globex_mysql
customer_initech_mysql
```

**使用示例**：

```bash
# 操作单个客户的全部主机
ansible customer_acme -m ping

# 操作单个客户的 MySQL（差异化备份策略自动从 group_vars 加载）
ansible-playbook playbooks/02-mysql-maintenance.yml -l customer_acme_mysql

# 全局巡检所有客户的 MySQL（使用默认阈值）
ansible-playbook playbooks/03-daily-inspection.yml -l role_mysql
```

## 三、客户 Profile 体系

### 3.1 Profile 文件结构

Profile 是客户差异化的**唯一数据源**，位于 `configs/customer-profiles/<customer-id>.yml`，包含 8 大维度：

| 维度 | 关键字段 | 驱动 |
|------|---------|------|
| 基本信息 | `customer_id` / `sla_level` | 标签、分组、报告 |
| 监控 | `monitoring.*` 阈值/采集间隔 | Prometheus 规则覆盖 |
| 告警 | `alerting.receivers` / `silence_windows` | Alertmanager 路由 |
| 安全 | `security.baseline_level` / `compliance` | Ansible 安全 Playbook |
| 备份 | `backup.retention` / `offsite_enabled` | 备份脚本参数 |
| 变更窗口 | `change_window.*` / `blackout_periods` | 变更审批流程 |
| 访问控制 | `access_control.ssh_access` / `team_members` | SSH 配置 |
| 报告 | `reporting.*` | 月报生成 |

**模板文件**：`configs/customer-profiles/EXAMPLE-customer.yml`

### 3.2 SLA 三级对照表

| 配置项 | premium | standard | basic |
|--------|---------|----------|-------|
| 采集间隔 | 10s | 15s | 30s |
| CPU Critical 阈值 | 90% | 85% | 85% |
| 备份保留(日) | 30 天 | 14 天 | 7 天 |
| 异地备份 | ✅ | 可选 | ❌ |
| 电话通知 | ✅ Critical | ❌ | ❌ |
| 安全基线 | CIS L2 | CIS L1 | CIS L1 |
| 日志保留 | 365 天 | 180 天 | 90 天 |
| 变更窗口 | 周六 00-04 | 周三 22-24 | 灵活协商 |
| 月报 | ✅ | ✅ | ❌ |

### 3.3 Profile 到配置的映射关系

```
Profile 字段                        配置产物
────────────────────────────────    ──────────────────────────────
customer_id                  ──→    Prometheus targets 的 customer 标签
                                    Inventory 的 customer_<id> 分组
sla_level                    ──→    group_vars 中的默认 SLA 变量集
monitoring.scrape_interval   ──→    Prometheus job 的 scrape_interval
monitoring.host.cpu_critical ──→    覆盖 rules/host.yml 的阈值（按客户 job）
alerting.receivers           ──→    alertmanager_multi_customer.yml 的 receiver
security.baseline_level      ──→    Ansible 安全 Playbook 的 cis_level 变量
backup.retention.daily       ──→    备份脚本的 --retention 参数
change_window.blackout       ──→    变更审批流程的 blackout 检查
access_control.ssh_access    ──→    sshd_config 的 AllowUsers / ProxyJump
```

## 四、监控差异化

### 4.1 采集目标差异化

Prometheus `file_sd` 目标文件中，每条 target 携带 `customer` 标签：

**文件**：`configs/targets/nodes_multi_customer.yml`

```yaml
- targets:
    - 10.10.2.10:9100
    - 10.10.2.11:9100
  labels:
    customer: acme        # 关键标签
    env: production
    cloud: aliyun
    role: mysql
    region: cn-east
```

所有 exporter 告警自动继承 `customer` 标签，驱动后续告警路由。

### 4.2 采集间隔差异化

在 Prometheus 主配置中，按客户 job 设置不同 `scrape_interval`：

```yaml
scrape_configs:
  # premium 客户：10s 采集
  - job_name: "node_acme"
    file_sd_configs:
      - files: ["targets/nodes_multi_customer.yml"]
    relabel_configs:
      - source_labels: [customer]
        regex: acme
        action: keep
    scrape_interval: 10s

  # standard 客户：15s
  - job_name: "node_globex"
    file_sd_configs:
      - files: ["targets/nodes_multi_customer.yml"]
    relabel_configs:
      - source_labels: [customer]
        regex: globex
        action: keep
    scrape_interval: 15s

  # basic 客户：30s
  - job_name: "node_initech"
    file_sd_configs:
      - files: ["targets/nodes_multi_customer.yml"]
    relabel_configs:
      - source_labels: [customer]
        regex: initech
        action: keep
    scrape_interval: 30s
```

### 4.3 告警阈值差异化

默认阈值定义在 `configs/rules/host.yml`。对需要差异化阈值的客户，在告警规则中使用 `for` + 标签匹配 + 外部标签注入实现覆盖。

**推荐方案**：为每个客户创建独立的规则文件片段，通过 `customer` 标签过滤：

```yaml
# configs/rules/host_acme.yml - acme 客户收紧的 CPU 阈值
groups:
  - name: host_acme
    rules:
      - alert: HighCpuAcme
        expr: |
          100 - (avg by(host)(rate(node_cpu_seconds_total{customer="acme",mode="idle"}[5m])) * 100) > 90
        for: 5m
        labels:
          severity: critical
          customer: acme
        annotations:
          summary: "CPU 使用率超过 90%（acme 收紧阈值）"
```

> **注意**：默认 `host.yml` 的告警需用 `customer!="acme"` 排除已覆盖客户，避免重复告警。

## 五、告警差异化

### 5.1 按客户路由

**文件**：`configs/alertmanager_multi_customer.yml`

核心机制：`group_by` 加入 `customer`，第一级子路由按 `customer` 标签分流，每个客户内部再按 `severity` 分级。

```yaml
route:
  group_by: ["alertname", "host", "cluster", "customer"]
  routes:
    # 客户 A 路由
    - matchers:
        - customer = "acme"
      receiver: "acme-default"
      routes:
        - matchers: [customer="acme", severity="critical"]
          receiver: "acme-critical"      # 电话 + webhook + email
        - matchers: [customer="acme", severity="major"]
          receiver: "acme-major"         # webhook + email
        - matchers: [customer="acme", severity=~"minor|warning"]
          receiver: "acme-minor"         # email only
      continue: false
    # 客户 B、C 同理...
```

### 5.2 抑制规则加入客户维度

防止跨客户误抑制：

```yaml
inhibit_rules:
  - source_matchers: ["alertname = \"HostDown\""]
    target_matchers: ["host =~ \".+\""]
    equal: ["host", "customer"]    # 关键：加入 customer
```

### 5.3 静默窗口差异化

客户业务低峰期的 minor/warning 告警静默，通过 Alertmanager API 创建按客户的 silence：

```bash
# acme 客户凌晨静默 minor 告警
amtool silence add \
  --comment="acme 低峰静默" \
  --duration=6h \
  --start="$(date -d 'tomorrow 00:00' +%FT%T)" \
  customer=acme severity=minor
```

也可通过 `time_intervals`（Alertmanager 0.22+）配置周期性静默：

```yaml
route:
  routes:
    - matchers: [customer="acme", severity=~"minor|warning"]
      receiver: "acme-minor"
      mute_time_intervals: ["acme-low-peak"]
      # ...

time_intervals:
  - name: "acme-low-peak"
    time_intervals:
      - times:
          - start_time: "00:00"
            end_time: "06:00"
        weekdays: ["monday:friday"]
```

## 六、安全差异化

### 6.1 安全基线等级

通过 group_vars 中的 `security_baseline_level` 变量，驱动 Ansible 安全 Playbook 执行不同强度的加固：

```yaml
# Playbook 中的条件判断示例
- name: CIS L2 - 禁用不必要的文件系统
  ansible.builtin.systemd:
    name: "{{ item }}"
    masked: yes
  loop:
    - cramfs
    - freevxfs
    - jffs2
    - hfs
    - hfsplus
    - squashfs
    - udf
  when: security_baseline_level == "cis-l2"

- name: CIS L1/L2 - 确保 SSH 禁用 root 登录
  ansible.builtin.lineinfile:
    path: /etc/ssh/sshd_config
    regexp: "^PermitRootLogin"
    line: "PermitRootLogin no"
  when: root_login == false
```

### 6.2 差异化矩阵

| 安全项 | premium (CIS L2) | standard (CIS L1) | basic (CIS L1) |
|--------|-----------------|-------------------|----------------|
| 防火墙策略 | strict（默认拒绝+白名单） | standard（默认开放常用端口） | standard |
| WAF (ModSecurity) | ✅ | ✅ | ❌ |
| HIDS (Wazuh) | ✅ | ✅ | ✅ |
| NIDS (Suricata) | ✅ | ✅ | ❌ |
| fail2ban | ✅ | ✅ | ✅ |
| 日志保留 | 365 天 | 180 天 | 90 天 |
| 审计日志 | ✅ 365 天 | ✅ 180 天 | ✅ 90 天 |
| 合规扫描 | 等保三级 + CIS | 等保二级 + CIS | CIS |

### 6.3 合规差异化

```yaml
# group_vars/customer_acme/vars.yml
security_compliance:
  - "等保三级"
  - "PCI-DSS"

# Playbook 中根据合规要求启用额外检查
- name: 等保三级 - 密码复杂度策略
  ansible.builtin.lineinfile:
    path: /etc/security/pwquality.conf
    regexp: "{{ item.key }}"
    line: "{{ item.key }} = {{ item.value }}"
  loop:
    - { key: minlen, value: "14" }
    - { key: minclass, value: "4" }
    - { key: maxrepeat, value: "3" }
  when: '"等保三级" in security_compliance'
```

```bash
# MySQL 备份 - premium 客户（从 group_vars 加载变量）
```

## 八、变更窗口与访问控制差异化

### 8.1 变更窗口

各客户的变更窗口和 blackout 期定义在 Profile 中，变更操作前须检查：

```bash
# 变更前检查脚本（示例逻辑）
# 1. 读取目标客户的 change_window 配置
# 2. 检查当前时间是否在 blackout 期内
# 3. 若在 blackout 期，拒绝执行（紧急变更除外）
```

| 客户 | 常规变更 | 重大变更 | Blackout 期 | 紧急变更 |
|------|---------|---------|------------|---------|
| acme | 周六 00-04 | 周六 00-04 | 工作日 9-18 / 月末 25-28 | 需审批 |
| globex | 周三 22-24 | 周六 00-04 | 工作日 9-18 | 需审批 |
| initech | 灵活协商 | 周六 00-04 | 无 | 允许 |

### 8.2 访问控制

| 控制项 | premium | standard | basic |
|--------|---------|----------|-------|
| SSH 方式 | 仅堡垒机 | 仅堡垒机 | 仅堡垒机 |
| root 登录 | ❌ | ❌ | ❌ |
| 审计 | ✅ 365 天 | ✅ 180 天 | ✅ 90 天 |
| 操作录屏 | ✅（JumpServer） | ✅ | ❌ |
| 团队成员 | Profile 指定 | Profile 指定 | Profile 指定 |

Ansible 中通过 `ssh_access_mode` 变量控制 SSH 配置：

```yaml
# group_vars 中
ssh_access_mode: "bastion_only"
bastion_host: "jumpserver"

# ansible.cfg 中配置跳板
# 或在 inventory 中设置 ansible_ssh_common_args
[customer_acme:vars]
ansible_ssh_common_args='-o ProxyJump=jumpserver'
```

## 九、操作 SOP

### SOP-1：新增客户纳管

```text
步骤 1  创建客户 Profile
        cp configs/customer-profiles/EXAMPLE-customer.yml \
           configs/customer-profiles/<new-id>.yml
        vi configs/customer-profiles/<new-id>.yml  # 填写客户实际要求

步骤 2  创建 group_vars
        mkdir -p playbooks/group_vars/customer_<new-id>/
        cp configs/customer-profiles/<new-id>.yml \
           playbooks/group_vars/customer_<new-id>/vars.yml

步骤 3  添加 Inventory 分组
        vi playbooks/inventory_multi_customer_example.ini
        # 新增 [customer_<new-id>_<role>] 主机段
        # 新增 [customer_<new-id>:children] 聚合段
        # 在 [role_<role>:children] 中加入该客户

步骤 4  添加监控目标
        vi configs/targets/nodes_multi_customer.yml
        # 新增该客户主机，labels 中加 customer: <new-id>

步骤 5  添加告警路由
        vi configs/alertmanager_multi_customer.yml
        # 新增 customer_<new-id> 路由段和对应 receivers

步骤 6  添加 Prometheus 采集 job（如采集间隔非默认）
        vi configs/prometheus.yml
        # 新增按 customer 标签 relabel 的 job

步骤 7  初始化主机
        ansible-playbook playbooks/00-init-host.yml -l customer_<new-id>

步骤 8  应用安全基线
        ansible-playbook playbooks/01-system-baseline.yml -l customer_<new-id>

步骤 9  验证告警路由
        # 手动触发一条带 customer 标签的告警，确认路由到正确 receiver

步骤 10 提交 Git
        git add -A && git commit -m "feat: 纳管新客户 <new-id>"
```

### SOP-2：修改客户监控阈值

```text
步骤 1  编辑客户 group_vars
        vi playbooks/group_vars/customer_<id>/vars.yml
        # 修改 monitoring_* 变量

步骤 2  （如需独立规则文件）创建/编辑按客户的告警规则
        vi configs/rules/host_<id>.yml

步骤 3  语法校验
        python3 -c "import yaml; yaml.safe_load(open('configs/rules/host_<id>.yml'))"

步骤 4  应用变更
        ansible-playbook playbooks/04-deploy-monitoring.yml -l monitoring
        # 或 reload Prometheus: curl -X POST http://prometheus:9090/-/reload

步骤 5  验证
        # 在 Prometheus UI 检查规则已加载
        # 确认告警状态正确

步骤 6  提交 Git
        git add -A && git commit -m "config: 调整 <id> 客户监控阈值"
```

### SOP-3：全局巡检（跨客户）

```text
步骤 1  按角色聚合巡检（使用默认阈值）
        ansible-playbook playbooks/03-daily-inspection.yml -l role_mysql
        ansible-playbook playbooks/03-daily-inspection.yml -l role_web

步骤 2  按客户巡检（使用客户差异化配置）
        ansible-playbook playbooks/03-daily-inspection.yml -l customer_acme

步骤 3  按云厂商巡检
        ansible-playbook playbooks/03-daily-inspection.yml -l aliyun
```

### SOP-4：客户变更操作

```text
步骤 1  检查变更窗口
        # 读取目标客户 Profile 中的 change_window 与 blackout_periods
        # 确认当前时间在允许的变更窗口内
```

## 十二、注意事项

1. **隔离性**：一个客户的 group_vars 变量不会泄漏到其他客户，Ansible 按主机组加载。
2. **默认兜底**：未在 Profile 中定义的字段，使用 `group_vars/all` 中的全局默认值。
3. **标签一致性**：Inventory 分组名、Prometheus 标签、Alertmanager matcher 中的 customer 值必须完全一致（如 `acme` 而非 `Acme`）。
4. **密钥安全**：所有 webhook URL、PagerDuty key、邮箱密码等敏感值使用 Ansible Vault 加密，禁止明文提交。
5. **增量迁移**：现有单客户配置（`alertmanager.yml` / `nodes.yml`）保留不动，多客户版为独立文件，可在验证后切换。
6. **网段约定**：建议按客户划分网段（如 acme=10.10.x.x），便于防火墙规则和监控目标管理。
