# 技能矩阵与能力评估

> 本文档系统梳理 devops-hub 项目从启动到完成所运用的全部技能，按技能域分类，
> 建立能力评估分级模型，并映射到具体交付物。既是对本项目能力的完整盘点，
> 也是团队后续招聘、培训、人员配置与项目复用的能力基线参考。

---

## 一、文档定位

| 维度 | 说明 |
|------|------|
| 目的 | 把"做了什么"背后的"需要什么能力"显性化、结构化、可评估化 |
| 适用对象 | 运维团队负责人（排兵布阵）、HR（招聘画像）、新成员（能力自评）、后续项目（能力缺口识别） |
| 与方法论的关系 | `12-方法论与设计原则.md` 回答"为什么这样做"，本文档回答"做成这件事需要哪些能力" |
| 与路线图的关系 | `10-实施路线图.md` 标注负责人（SRE/DBA/安全），本文档细化每类角色的技能要求 |

---

## 二、能力评估分级模型

采用五级熟练度模型，量化每个技能的掌握程度：

| 等级 | 名称 | 定义 | 能否独立交付 |
|------|------|------|------------|
| L1 | 了解 | 知道概念，能在指导下执行 | 否 |
| L2 | 熟悉 | 能独立完成标准任务 | 部分 |
| L3 | 熟练 | 能独立设计与交付，处理异常 | 是 |
| L4 | 精通 | 能优化、调优、培训他人、制定规范 | 是，且可引领 |
| L5 | 专家 | 能创新方法论、解决前沿难题、行业输出 | 是，且可定义标准 |

> 建议每个角色对其负责域技能达到 **L3 以上**，核心域技能达到 **L4**。

## 六、技能缺口识别与建设建议

### 6.1 识别方法
1. 对照第四节矩阵，对现有团队成员逐技能自评（L1-L5）；
2. 与"建议等级"对比，标记 **低于建议等级** 的为缺口；
3. 缺口集中在某域 -> 该域为团队短板，需补强。

### 6.2 常见缺口与补强路径

| 短板域 | 补强方式 | 周期 |
|--------|---------|------|
| K8s 安全 | kube-bench 实操、CIS K8s Benchmark 研读 | 2-4 周 |
| 入侵检测 | Wazuh/Suricata 规则调优实战、ATT&CK 学习 | 4-8 周 |
| 方法论沉淀 | 复盘演练、撰写复盘报告、套用 `12` 自检清单 | 持续 |
| Git 钩子工程 | 阅读 `hooks/` 源码、扩展检查项 | 1-2 周 |
| 威胁情报 | 接入 AbuseIPDB/OTX、编写匹配脚本 | 2-4 周 |

### 6.3 能力建设长效机制
- **复盘文化**：每次故障/演练必复盘，输出改进项；
- **轮岗机制**：SRE/DBA/安全跨域轮岗，减少单点能力依赖；
- **知识库**：复盘报告、SOP、技能笔记沉淀进 `docs/`；
- **认证引导**：鼓励 CKA（K8s）、RHCE、CISSP 等认证，对齐标准层。

## 七、项目复用时的能力自检

后续项目套用本仓库时，先用下表评估团队能力是否覆盖：

- [ ] 至少 1 人具备架构设计能力（L4）
- [ ] 至少 1 人精通可观测性体系（L4）
- [ ] 至少 1 人精通 K8s 运维（L4）
- [ ] 至少 1 人精通数据库运维（L4）
- [ ] 至少 1 人熟练安全工程（L3+）
- [ ] 至少 1 人熟练 Ansible/Shell 自动化（L4）
- [ ] 至少 1 人熟练 Git 工程规范（L3+）
- [ ] 团队具备方法论与标准对标意识（L3+）
- [ ] 团队具备文档与沟通能力（L3+）
- [ ] 团队具备验证与排障执行能力（L3+）

> 任一项不满足，建议先补强或引入外部支持，再启动项目，避免能力缺口拖慢落地。

#### 9.8.2 重点推荐：devops-sre-skills

[bregman-arie/devops-sre-skills](https://github.com/bregman-arie/devops-sre-skills) 是最契合本项目的开源资源，原因：

1. **设计理念一致**：其 README 声明"Safe by default（默认只读）"、"No secrets（无密钥）"、"含验证与回滚指引"--与本仓库方法论（`docs/12`）的安全左移、纵深防御、IaC 原则高度吻合。
2. **分类覆盖核心域**：observability / kubernetes / security / incident / cost / terraform / aws，几乎一一对应本项目缺口。
3. **格式标准**：每个 skill 含 YAML frontmatter（tools/safety 契约）+ Markdown 步骤，与已安装的 understand/changelog-generator skill 格式同构。
4. **作者权威**：作者 Arie Bregman 是知名 SRE、《Learn DevOps》系列作者，内容专业可靠。

其已覆盖的本项目缺口：

| 本项目缺口 | 对应 skill | 说明 |
|-----------|-----------|------|
| K8s 运维 | `diagnose-crashloop`、`diagnose-imagepullbackoff`、`triage-node-pressure`、`triage-pending-pods`、`triage-service-dns` | 覆盖 K8s 最常见 5 类故障诊断 |
| 监控告警 | `triage-error-budget-burn`、`triage-latency-regression` | 错误预算与延迟回归，补本项目 SLO 量化缺口 |
| 安全 | `triage-suspected-secret-exposure` | 密钥泄露应急 |
| 应急响应 | `sev1-first-15-minutes` | Sev1 事故黄金 15 分钟 SOP，补 MTTR 压缩 |
| 成本(FinOps) | `triage-cost-spike` | 成本飙升排查，补成本意识缺口 |

git clone https://github.com/bregman-arie/devops-sre-skills.git /tmp/devops-sre-skills
