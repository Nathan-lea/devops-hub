# 监控体系方案

## 一、监控总体设计

### 1.1 监控分层
```
业务层   → 接口可用性、订单/登录成功率
应用层   → JVM、Go runtime、慢查询数
中间件层 → MySQL/TiDB/Redis/Nginx 指标
容器层   → Pod 状态、容器 OOM、Deployment 副本数
主机层   → CPU/内存/磁盘/网络/磁盘 IO
网络层   → 端口存活、TCP 延迟、DNS 解析
```

### 1.2 监控覆盖矩阵

| 监控对象 | 采集组件 | 关键指标 | 采集频率 |
|----------|----------|----------|----------|
| Linux 主机 | node_exporter | cpu/mem/disk/net/load | 15s |
| MySQL | mysqld_exporter | QPS/TPS/连接数/慢查询/主从延迟 | 15s |
| TiDB | PD + TiKV metrics | region 数/存储容量/慢查询 | 15s |
| Redis | redis_exporter | 内存/连接/QPS/命中率/主从 | 15s |
| Nginx | nginx_exporter / stub_status | 请求数/状态码/连接数 | 15s |
| K8s | kube-state-metrics + cAdvisor | Pod/Node/Deployment 状态 | 30s |
| 端口/HTTP | blackbox_exporter | 可达性/响应时间/证书过期 | 30s |
| 进程 | process-exporter | 关键进程存活 | 15s |

## 二、Prometheus 部署架构

### 2.1 部署拓扑（建议双副本）
```
                 ┌──────────────────────┐
   Grafana ────→ │  Prometheus 主       │ ←── Alertmanager
                 │  Prometheus 备(只读) │
                 └──────────┬───────────┘
                            │
        ┌───────────────────┼───────────────────┐
        ▼                   ▼                   ▼
   pull 方式             push 网关             服务发现
  (静态/SD)           (pushgateway)         (K8s/Consul)
```

### 2.2 推荐规格
| 主机规模 | Prometheus 规格 | 保留时长 | 预估存储 |
|----------|------------------|----------|----------|
| ≤50 台 | 4C8G + 200G SSD | 15 天 | ~80G |
| 50~150 台 | 8C16G + 500G SSD | 30 天 | ~200G |
| >150 台 | 16C32G + 1T SSD | 30~90 天 | ~500G |

> 100 台主机推荐：8C16G + 500G SSD，保留 30 天，配合 Thanos/VictoriaMetrics 做长期存储。

## 三、采集端部署

### 3.1 node_exporter 标准化部署（Ansible）

详见 `playbooks/deploy_node_exporter.yml`，核心要点：
- 监听端口统一为 `9100`
- 只允许内网访问（防火墙限制）
- systemd 管理，开机自启
- 采集间隔 15s

### 3.2 中间件 exporter 部署清单

| 组件 | 端口 | 部署方式 | 配置要点 |
|------|------|----------|----------|
| mysqld_exporter | 9104 | 旁路部署 | 创建只读监控账号 |
| redis_exporter | 9121 | 旁路部署 | 使用只读密码或 ACL |
| nginx_exporter | 9113 | 旁路部署 | 开启 stub_status |
| blackbox_exporter | 9115 | 集中部署 | 统一探活 |
| tidb监控 | 2379/20180 | PD 节点自带 | 直接 scrape PD/TiKV/TiDB |

### 3.3 Prometheus 抓取配置（scrape_configs）

详见 `configs/prometheus.yml`。

## 四、Grafana 看板规划

### 4.1 看板分层
1. **全局概览**：主机健康度、中间件健康度、K8s 概览、告警数
2. **主机详情**：单机 CPU/内存/磁盘/网络历史
3. **MySQL 详情**：QPS、连接池、慢查询、主从延迟
4. **TiDB 详情**：Region 分布、慢查询、存储增长
5. **Redis 详情**：内存、命中率、BigKey
6. **K8s 详情**：Pod 资源、Node 资源、事件流
7. **网络探活**：端口/HTTP 可用性

## 五、容量规划与长期存储

### 5.1 Prometheus 本地存储优化
```yaml
# prometheus.yml 片段
storage:
  tsdb:
    retention.time: 30d
    retention.size: 400GB
    out_of_order_time_window: 30m
```

### 5.2 长期存储选型
| 方案 | 优点 | 缺点 | 推荐场景 |
|------|------|------|----------|
| **VictoriaMetrics** | 资源占用低、压缩好、部署简单 | 生态略新 | 中小规模首选 ✅ |
| Thanos | 官方生态、多集群联邦 | 部署复杂、依赖对象存储 | 多集群/超大规模 |
| Mimir | Grafana 官方、水平扩展 | 资源占用高 | 超大规模 |

> 100 台规模推荐 **VictoriaMetrics 单节点**，后续可平滑升级到集群版。
