# 运维系统建设方法论与设计原则

> 本文档系统阐述本服务器运维系统方案所遵从的**思想、原理、原则、方法、标准、步骤**，
> 并将每一项映射到本项目的具体交付物，形成可复用的"方法论 + 模板"基线，
> 供后续同类项目（中等规模、多云异构、Linux 为主）直接套用参考。

---

## 〇、前言：为什么要沉淀方法论

一个能落地的运维系统，区别于"一堆工具堆叠"的关键在于：它背后有一套**自洽的思想体系**在统一指挥。
工具会迭代、版本会更新、人员会流动，唯有方法论是团队可继承、可复用、可审计的资产。

本项目沉淀方法论的目的有三：

1. **可复用**——下一个项目不必从零摸索，按本框架填空即可启动；
2. **可解释**——每一个技术选型、每一层架构都能回答"为什么这样做"；
3. **可演进**——方法论是骨架，工具是肌肉，骨架稳定则换肌无痛。

本文档按 **思想层 → 原理层 → 原则层 → 方法层 → 标准层 → 步骤层 → 落地映射 → 复用模板** 的层次组织，
最后给出方法论自检清单，确保后续项目不偏离主线。

## 一、指导思想（思想层）

思想层是最高层的价值观与方法论哲学，决定了"我们用什么样的世界观来看待运维"。

### 1.1 SRE 思想：用工程方法解决运维问题
源自 Google《Site Reliability Engineering》。核心主张：
- 把运维当作软件工程问题，用**代码、自动化、数据**替代手工操作；
- 以 **SLI/SLO/SLA** 量化可靠性，用错误预算（Error Budget）平衡稳定与速度；
- 消除劳动（Toil），将重复性工作工程化。

**本项目体现**：自动化覆盖率目标 80%+；监控、巡检、备份、安全检测全部脚本化/Playbook 化（见 `scripts/`、`playbooks/`）；告警分级与 SLO 量化（见 `08-告警与应急方案.md`）。

### 1.2 DevOps 思想：开发与运维协同，一切皆代码
强调打破开发/运维壁垒，以**版本化、流水线、持续反馈**驱动交付。
- **基础设施即代码（IaC）**：所有配置进 Git，变更可追溯、可回滚；
- **GitOps**：以 Git 仓库作为系统期望状态的唯一真实来源（Single Source of Truth）。

**本项目体现**：Ansible + Git 管理全部主机配置（`03-配置管理方案.md`）；inventory、Playbook、模板、规则全部版本化（见 `playbooks/`、`configs/`）。

### 1.3 可观测性优先（Observability First）
可观测性是运维的"眼睛"。在没有可见性之前，一切优化都是盲人摸象。
主张**先看见，再治理**：先建立指标/日志/链路三支柱，再谈容量、安全、性能优化。

**本项目体现**：实施路线图把"监控告警期（阶段二）"排在"深化治理期（阶段三）"之前（见 `10-实施路线图.md`）；监控体系（`01`）、日志体系（`02`）是优先级最高的两个分册。

### 1.4 主动预防优于被动救火（Proactive > Reactive）
从"出事再修"转向"预测并预防"。通过趋势告警、容量预测、基线扫描，把故障消灭在萌芽。

**本项目体现**：容量趋势告警（`configs/rules/host.yml`）、证书提前续期（`scripts/cert_check.sh`）、安全基线扫描（`06-安全合规方案.md`）、备份恢复演练（`07`）。

### 1.5 安全左移与纵深防御（Shift-Left Security & Defense in Depth）
- **安全左移**：在建设初期而非上线后才考虑安全，基线、密钥、最小权限贯穿全流程；
- **纵深防御**：不依赖单点防护，从网络边界 → 主机 → 应用 → 数据，多层检测与响应，任一层被突破仍有后续防线。

**本项目体现**：阶段一即做系统基线加固（`01-system-baseline.yml`）；安全方案覆盖网络层（Suricata/防火墙）、主机层（Wazuh/auditd）、应用层（WAF）、容器层（Falco）、数据层（备份加密）（见 `11-入侵检测与网络安全方案.md`）。

### 1.6 度量驱动，数据决策（Measure Everything）
"没有度量就没有改进"。一切判断基于数据而非直觉：资源利用率、告警噪声、MTTR、备份成功率、漏洞修复率均需量化。

**本项目体现**：备份脚本写 node_exporter textfile 指标复用监控体系（`07`）；告警规则 76 条覆盖各维度（`configs/rules/`）；报表体系（`09`）。

### 1.7 渐进式落地（Progressive Delivery / MVP）
罗马不是一天建成的。先 MVP 跑通主链路，再迭代深化。避免"大而全一次性上线"导致周期失控。

**本项目体现**：4 阶段 12 周路线图，每阶段有明确里程碑与验收（`10`）；WAF 先检测模式 1-2 周再切阻断（`11`）。

## 二、理论基础（原理层）

原理层是指导具体技术决策的科学规律与工程定理。

### 2.1 可观测性三支柱
- **Metrics（指标）**：聚合数值，回答"发生了什么、趋势如何"；
- **Logs（日志）**：离散事件，回答"具体细节是什么"；
- **Traces（链路）**：请求路径，回答"问题出在哪一跳"。

三者互补：指标用于告警与趋势，日志用于根因，链路用于跨服务定位。本项目用 Prometheus（指标）+ Loki（日志）+ Tempo（链路）构成同构生态，降低运维成本。

### 2.2 Google SRE 四大黄金信号
监控任何系统，应覆盖四个维度：
| 信号 | 含义 | 本项目示例 |
|------|------|-----------|
| 延迟 Latency | 请求处理耗时 | Nginx 请求延迟、MySQL 慢查询 |
| 流量 Traffic | 系统承载量 | QPS、连接数、K8s Pod 副本数 |
| 错误 Errors | 错误率 | HTTP 5xx、MySQL 错误连接、探活失败 |
| 饱和度 Saturation | 资源使用程度 | CPU/内存/磁盘/inode、连接池 |

本项目告警规则设计遵循此四维度，避免只盯 CPU/内存的片面监控。

### 2.3 SLI / SLO / SLA 与错误预算
- **SLI**（服务等级指标）：可度量的质量指标（如可用性 99.9%）；
- **SLO**（服务等级目标）：对 SLI 设定的目标值；
- **SLA**（服务等级协议）：对外承诺，违约有后果；
- **错误预算**：SLO 允许的不可用时间（如 99.9% = 每月约 43 分钟）。错误预算耗尽则冻结发布、优先稳定性。

本项目核心系统目标 SLA 99.9%、MTTR < 30 分钟（见 `00`）。

### 2.4 纵深防御原理（Defense in Depth）
单一安全控制必被突破，需多重独立控制叠加，使攻击者需连续突破多层才能得手。
本项目构建七层防御：网络防护层 → IDS 入侵检测层 → 存储处理层 → 采集层 → 安全分析响应层 → 展示告警层 → 主机层（见 `00` 架构分层图）。

### 2.5 最小权限原理（Least Privilege）
任何主体（用户、进程、Pod）只授予完成职责所需的最小权限。
本项目体现：运维用户分离、sudo 白名单、K8s RBAC + NetworkPolicy 默认拒绝、Pod Security Standards restricted（`configs/k8s/`）。

### 2.6 故障域隔离原理
通过隔离限制故障爆炸半径，使单点故障不致全局瘫痪。
本项目体现：K8s 节点污点/亲和、NetworkPolicy 网络分段、数据库主从隔离、监控主备、备份 3-2-1 异地存放。

### 2.7 可靠性工程：MTBF / MTTR
- **MTBF**（平均故障间隔）：反映系统健壮性，越大越好；
- **MTTR**（平均修复时间）：反映恢复能力，越小越好。

提升 MTBF 靠预防（基线、容量、备份），压缩 MTTR 靠应急 SOP、自愈、监控。本项目目标 MTTR < 30 分钟，配套应急 SOP（`08`）与自愈脚本（`09`）。

### 2.8 告警疲劳与告警收敛原理
告警过多会导致"狼来了"效应，有效告警被淹没。需通过**分级、聚合、抑制、静默**收敛噪声。
本项目体现：Alertmanager 4 级路由（P0-P3）+ 抑制规则（如主机宕机时抑制其上服务告警）（`configs/alertmanager.yml`）、告警演练与噪声治理（`10` 阶段二 W6）。

### 2.9 安全领域的海因里希法则与墨菲定律
- **海因里希法则**：1 起重大事故背后有 ~300 起未遂，需重视异常告警与未遂事件；
- **墨菲定律**：可能出错的事终将出错，需假设故障必然发生并预先准备恢复方案。

本项目体现：异常连接、暴力破解等"未遂"事件全部告警（`configs/rules/security.yml` 27 条）；备份恢复演练与灾备演练常态化（`07`、`10`）。

### 2.10 不可变基础设施（Immutable Infrastructure）
基础设施一旦部署不再手工修改，变更通过重新部署新版本完成，保证环境一致性与可复现。
本项目体现：Ansible 幂等 Playbook 保证配置可重复执行；K8s 声明式编排；镜像化部署。

## 三、核心设计原则（原则层）

原则层是设计时必须遵守的准则，是原理向工程实践的转译。

### 3.1 统一管控，避免烟囱
一套平台纳管多云异构主机，禁止各云各团队自建监控/日志孤岛。
→ Ansible 统一配置、Prometheus 统一采集、Grafana 统一看板。

### 3.2 分层解耦，各层独立演进
采集 → 存储 → 处理 → 展示 → 告警 → 响应，各层接口标准化，单层升级不影响整体。
→ 换存储从 Prometheus 到 VictoriaMetrics 无需改采集层。

### 3.3 基础设施即代码，变更可追溯
一切配置进 Git，禁止手工登机改配置；变更走 MR 评审 + CI 校验。
→ `configs/`、`playbooks/`、`scripts/` 全部版本化。

### 3.4 标准化优先于定制化
能用标准方案就不自研；命名、目录、端口、标签统一规范。
→ 选用 Prometheus/Grafana/Loki/Wazuh 等主流开源，降低学习与招聘成本。

### 3.5 自动化优先，消除 Toil
重复操作必自动化；无法自动化的需有 SOP 文档兜底。
→ 巡检、备份、安全检测、基线加固全部自动化。

### 3.6 幂等与可重入
脚本/Playbook 可重复执行且结果一致，中断后可续跑。
→ Ansible Playbook 幂等设计；备份脚本支持增量与断点续传。

### 3.7 安全左移 + 纵深防御
建设初期即落地安全基线；多层独立防御，不押注单点。
→ 阶段一基线加固；七层防御架构。

### 3.8 最小权限 + 默认拒绝
权限按需授予，网络/资源默认拒绝放行。
→ RBAC、NetworkPolicy、sudo 白名单、防火墙默认 DROP。

### 3.9 主动预防 + 趋势前置
不只告警当下阈值，更要预测趋势（磁盘将满、证书将过期）。
→ 容量预测告警、证书提前 30 天告警。

### 3.10 渐进式落地 + MVP 验证
先跑通主干再深化；高风险变更先检测后阻断、先灰度后全量。
→ 4 阶段路线图；WAF 检测优先；告警先上线再噪声治理。

### 3.11 可观测、可度量、可复盘
所有操作留痕，关键动作有指标，故障必复盘形成改进项。
→ 备份成功率指标、告警审计、应急 SOP 含复盘流程（`08`）。

### 3.12 成本意识（FinOps）
资源按需而非过度预留，利用率可视化，存储分层冷热。
→ VictoriaMetrics 长期存储降本、MinIO 对象存储分层、资源 Quota 限制（`configs/k8s/`）。

## 四、建设方法论（方法层）

方法层是"怎么做"的工程方法，提供可操作的思维框架。

### 4.1 自顶向下设计 + 自底向上实施
- **设计**：先定目标与架构（顶层），再分解到模块；
- **实施**：先搭基础（纳管/采集），再叠加治理（监控/安全/备份）。

本项目先出 `00 总体架构` 定全局，再分册细化；实施则从"主机纳管 + 基线"做起。

### 4.2 分层架构法
将复杂系统按职责分层，每层定义清晰输入/输出。本项目七层架构（见 `00`）即此方法产物，便于并行开发与独立演进。

### 4.3 PDCA 持续改进循环
- **Plan**：制定目标与计划（路线图、SLO）；
- **Do**：执行建设与部署；
- **Check**：监控/巡检/演练验证效果；
- **Act**：复盘改进，进入下一轮。

本项目 4 阶段路线图本身即一个 PDCA 大循环；日常巡检→告警→修复→复盘是小循环。

### 4.4 OODA 循环（安全应急响应）
- **Observe 观察**：监控/IDS 发现异常；
- **Orient 判断**：关联分析、威胁情报比对；
- **Decide 决策**：定级、选择响应动作；
- **Act 行动**：封禁/隔离/取证/恢复。

本项目安全事件应急 SOP（`11`、`08`）按此循环设计：检测 → 关联 → 响应 → 复盘。

### 4.5 故障树分析（FTA）与 FMEA
- **FTA**：从顶事件（如"数据库不可用"）向下分解根因树；
- **FMEA**：枚举各组件失效模式与影响，预先设计缓解。

用于设计告警规则与应急 SOP，确保覆盖关键失效路径。

### 4.6 ITIL 服务管理方法
借鉴 ITIL 的事件管理、问题管理、变更管理、配置管理流程：
- **事件管理**：尽快恢复服务（应急 SOP）；
- **问题管理**：找根因，防止复发（复盘 + 改进项）；
- **变更管理**：变更评审、灰度、回滚预案（IaC + MR）；
- **配置管理**：CMDB 资产台账（`00`、`03`）。

### 4.7 5W2H 分析法
用于需求澄清与方案描述：What/Why/Who/When/Where/How/How much。本项目各分册与路线图均隐含此结构（背景/目标/负责人/时间/方法/预算）。

### 4.8 RACI 责任矩阵
明确每项任务的 Responsible（执行）/ Accountable（负责）/ Consulted（咨询）/ Informed（知会）。本项目路线图标注负责人（SRE/DBA/安全），是简化版 RACI。

### 4.9 风险评估方法
识别资产 → 评估威胁与脆弱性 → 计算风险 → 选择处置（缓解/转移/接受/规避）。用于安全方案优先级排序（`06`、`11`）。

### 4.10 威胁建模（STRIDE / MITRE ATT&CK）
- **STRIDE**：从伪装、篡改、否认、信息泄露、拒绝服务、提权六类威胁建模；
- **MITRE ATT&CK**：以攻击者战术与技术矩阵对照防御覆盖。

本项目入侵检测覆盖初始访问、执行、持久化、横向移动、渗出等战术（`11`）。

## 六、实施步骤与方法（步骤层）

步骤层是落地执行的顺序与方法，确保"先有地基后有高楼"。

### 6.1 总体步骤（六步法）
```
①需求调研 → ②架构设计 → ③技术选型 → ④分阶段实施 → ⑤验收运营 → ⑥持续演进
```

#### 步骤① 需求调研
- 盘点资产：主机规模、发行版、云来源、中间件（本项目约 100 台、Debian/Ubuntu/CentOS、MySQL/TiDB/Redis/K8s）；
- 明确目标：SLA、自动化率、安全合规要求；
- 约束识别：预算、人员、网络限制、合规义务。

#### 步骤② 架构设计
- 输出总体架构与分层（`00`）；
- 确定管控拓扑（管控节点/监控中心/安全中心/被管主机）；
- 定义各模块边界与接口。

#### 步骤③ 技术选型
- 按"标准化优先 + 生态同构 + 规模匹配"原则选型；
- 100 台规模选轻量方案（Loki 而非 ELK、VictoriaMetrics 长期存储）；
- 异构主机选 Agentless（Ansible）。

#### 步骤④ 分阶段实施（4 阶段 12 周）
| 阶段 | 周期 | 主题 | 核心交付 |
|------|------|------|---------|
| 一 基础建设期 | W1-2 | 纳管+基线 | Ansible、CMDB、SSH、基线加固、备份基线 |
| 二 监控告警期 | W3-6 | 可观测性 | Prometheus、Grafana、Loki、Alertmanager、告警规则 |
| 三 深化治理期 | W7-9 | 治理+安全+容灾 | 数据库治理、K8s 加固、安全合规、备份演练 |
| 四 持续运营期 | W10-12 | 自动化运营 | AWX、巡检、自愈、报表、SOP、灾备演练 |

每阶段设里程碑与验收标准，避免无界推进。

#### 步骤⑤ 验收运营
- 全量验收报告；
- SOP 上线、值班机制建立；
- 首次灾备演练通过。

#### 步骤⑥ 持续演进
- 复盘改进项进入 backlog；
- 演进方向：FinOps 成本优化、混沌工程、AIOps、CMDB 深化、堡垒机等。

### 6.2 单项落地步骤模板（适用于任一新增能力）
对于新增任一运维能力（如新增一类监控、新增一类安全检测），统一套用以下 7 步：
1. **需求与范围**：要解决什么问题、覆盖哪些对象；
2. **设计与选型**：架构图、选型理由、是否符合原则；
3. **配置与脚本**：写进 `configs/`/`playbooks/`/`scripts/`，版本化；
4. **告警与看板**：定义 SLI/告警规则/Grafana 看板；
5. **灰度与验证**：先小范围/检测模式，验证无误报；
6. **全量与文档**：全量部署，更新对应分册文档与交叉引用；
7. **运营与复盘**：纳入巡检/演练，定期复盘优化。
