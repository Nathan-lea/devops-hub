# 数据库运维方案（MySQL / TiDB / Redis / PostgreSQL）

## 一、MySQL 运维

### 1.1 架构建议
```
                    ┌──────────────┐
   应用 ──────────->│  ProxySQL/   │
                    │  HAProxy     │
                    └──────┬───────┘
                           │
              ┌────────────┴────────────┐
              ▼                          ▼
        ┌──────────┐              ┌──────────┐
        │ Master   │ ──半同步──>  │ Slave-1  │
        │ (写)     │              │ (读)     │
        └──────────┘              └──────────┘
                                         │
                                    ┌──────────┐
                                    │ Slave-2  │
                                    │ (读/备份) │
                                    └──────────┘
```
- 写节点 1 台 + 读节点 1~2 台
- 读写分离用 ProxySQL 或应用层
- 主从同步建议半同步（semi-sync）

### 1.2 日常运维要点

#### 1.2.1 备份策略
| 类型 | 工具 | 频率 | 保留 | 存储位置 |
|------|------|------|------|----------|
| 全量物理备份 | xtrabackup | 每日 02:00 | 7 天 | 本地 + 对象存储 |
| 增量备份 | xtrabackup --incremental | 每 6 小时 | 3 天 | 对象存储 |
| Binlog 备份 | mysqlbinlog | 实时 | 30 天 | 对象存储 |
| 逻辑备份 | mysqldump | 每周日 | 30 天 | 对象存储 |

#### 1.2.2 Binlog 备份脚本逻辑
1. `mysqlbinlog --read-from-remote-server --raw` 持续拉取
2. 按小时切分文件
3. 上传对象存储（rclone）
4. 保留 30 天

#### 1.2.3 慢查询治理
- 开启 slow_query_log，阈值 1s
- 每天 03:00 用 pt-query-digest 分析，生成报告
- Top 10 慢 SQL 提交研发优化
- 配合 mysqld_exporter 慢查询数告警

#### 1.2.4 主从健康检查（Ansible 定时任务）
- 检查 `SHOW SLAVE STATUS\G` 中 `Slave_IO_Running` / `Slave_SQL_Running`
- 检查 `Seconds_Behind_Master` < 60s
- 异常触发告警

#### 1.2.5 关键参数基线
| 参数 | 推荐值 | 说明 |
|------|--------|------|
| innodb_buffer_pool_size | 物理内存 70% | 核心性能参数 |
| max_connections | 1000~2000 | 按业务调整 |
| innodb_log_file_size | 1G~2G | Redo log |
| binlog_expire_logs_seconds | 259200 (3天) | 磁盘控制 |
| slow_query_log | ON | 慢查询 |
| long_query_time | 1 | 阈值 |
| character_set_server | utf8mb4 | 字符集 |
| innodb_flush_method | O_DIRECT | 避免双缓冲 |

### 1.3 MySQL 告警规则
| 告警 | 条件 | 级别 |
|------|------|------|
| 主从中断 | mysql_slave_status_slave_io_running == 0 | Critical |
| 复制延迟 | mysql_slave_lag_seconds > 120 | Major |
| 连接数过高 | mysql_global_status_threads_connected / max_connections > 0.8 | Major |
| 慢查询激增 | rate(mysql_global_status_slow_queries[5m]) > 10 | Minor |
| 磁盘使用 | 磁盘 > 85% | Major |
| 实例宕机 | up == 0 持续 1m | Critical |

## 二、TiDB 运维

### 2.1 架构理解
```
┌───────┐   ┌───────┐   ┌───────┐
│ TiDB  │   │ TiDB  │   │ TiDB  │   <- SQL 层（无状态）
└───┬───┘   └───┬───┘   └───┬───┘
    └───────────┼───────────┘
                ▼
        ┌───────────────┐
        │   PD (调度)    │  <- 放置驱动
        └───────┬───────┘
                ▼
   ┌────────┐ ┌────────┐ ┌────────┐
   │ TiKV   │ │ TiKV   │ │ TiKV   │  <- 存储（Raft）
   └────────┘ └────────┘ └────────┘
```

### 2.2 监控要点
TiDB 自带完整监控体系（PD 20180 端口），关键看板：
- **Overview**：QPS、延迟、错误率
- **TiKV-Detail**：Region 数、CF 大小、RocksDB
- **PD**：Region 调度、Store 均衡
- **TiDB-Binlog**：同步状态

### 2.3 关键运维操作

#### 2.3.1 扩缩容
```bash
# 扩容 TiKV 节点（使用 tiup）
tiup cluster scale-out tidb-cluster scale-tikv.yaml

# 缩容（先迁数据再下线）
tiup cluster display tidb-cluster
# 确认 store 状态后执行
tiup cluster scale-in tidb-cluster -N 10.0.4.21:20160
```

#### 2.3.2 版本升级
```bash
# 离线升级（滚动）
tiup cluster upgrade tidb-cluster v7.5.0
# 在线升级（灰度）
tiup cluster upgrade tidb-cluster v7.5.0 --online
```

#### 2.3.3 备份恢复
```bash
# 全量备份（BR 工具备份到 S3）
br backup full \
  --pd "10.0.4.10:2379" \
  --storage "s3://tidb-backup/full-$(date +%Y%m%d)" \
  --s3.endpoint "http://minio:9000"

# 恢复
br restore full \
  --pd "10.0.4.10:2379" \
  --storage "s3://tidb-backup/full-20260101"
```

#### 2.3.4 慢查询分析
- TiDB Dashboard → Slow Queries
- 系统表 `INFORMATION_SCHEMA.SLOW_QUERY`
- 索引诊断：`EXPLAIN ANALYZE`

### 2.4 TiDB 告警规则
| 告警 | 条件 | 级别 |
|------|------|------|
| PD leader 丢失 | pd_tso_duration > 1s | Critical |
| Region 不均衡 | max(region_count) / avg > 1.3 | Major |
| TiKV 节点宕机 | tikv_engine_size == 0 | Critical |
| 存储增长过快 | deriv(storage_size[1h]) > 阈值 | Minor |
| 慢查询 | tidb_query_duration > 5s | Major |

## 三、Redis 运维

### 3.1 架构建议
- **主从 + 哨兵**：适合中小规模，自动故障转移
- **Cluster**：适合大数据量/高并发，分片
- 100 台规模推荐：1 主 2 从 + 3 哨兵，或 Cluster（3 主 3 从）

### 3.2 日常运维要点

#### 3.2.1 备份策略
| 类型 | 方式 | 频率 | 保留 |
|------|------|------|------|
| RDB 快照 | BGSAVE + rclone | 每日 02:00 | 7 天 |
| AOF 文件 | appendonly yes + 定期备份 | 实时 | 7 天 |
| 配置文件 | Ansible 管理 | 变更时 | Git 版本 |

#### 3.2.2 内存治理
- 设置 `maxmemory`，按实例规格 70%
- 淘汰策略：`allkeys-lru`（缓存）或 `noeviction`（持久化）
- 定期检查 BigKey：`redis-cli --bigkeys`
- 内存碎片率监控：`mem_fragmentation_ratio`
- 配置 `activedefrag yes`（4.0+）

#### 3.2.3 主从同步检查
```bash
# 检查从节点同步状态
redis-cli -h redis-slave-01 INFO replication
# 关注 master_link_status:down / master_last_io_seconds_ago
```

#### 3.2.4 关键参数基线
| 参数 | 推荐值 | 说明 |
|------|--------|------|
| maxmemory | 物理内存 70% | 防止 OOM |
| maxmemory-policy | allkeys-lru | 淘汰策略 |
| appendonly | yes | AOF 持久化 |
| appendfsync | everysec | 性能/安全平衡 |
| timeout | 300 | 空闲连接超时 |
| maxclients | 10000 | 最大连接 |
| requirepass | 强密码 | 安全 |
| rename-command | 禁用 FLUSHALL/KEYS | 误操作防护 |

### 3.3 Redis 告警规则
| 告警 | 条件 | 级别 |
|------|------|------|
| 实例宕机 | up == 0 | Critical |
| 内存使用高 | redis_memory_used / maxmemory > 0.85 | Major |
| 内存碎片 | mem_fragmentation_ratio > 1.5 | Minor |
| 连接数高 | connected_clients > 8000 | Major |
| 主从断开 | master_link_status == down | Critical |
| 持久化失败 | rdb_last_bgsave_status != ok | Major |

## 四、PostgreSQL 运维

### 4.1 架构建议
```
                    ┌──────────────┐
   应用 ──────────->│  PgBouncer/  │
                    │  Pgpool-II   │
                    └──────┬───────┘
                           │
              ┌────────────┴────────────┐
              ▼                          ▼
        ┌──────────┐   流复制      ┌──────────┐
        │ Primary  │ ──同步/异步──> │ Standby  │
        │ (读+写)  │                │ (只读)   │
        └──────────┘                └──────────┘
```
- 主从流复制：1 主 1~2 从，推荐同步复制（synchronous_commit=on）保证零数据丢失
- 连接池：PgBouncer（轻量连接池）或 Pgpool-II（连接池 + 负载均衡 + 读写分离）
- 高可用：Patroni + etcd 自动故障转移，或 repmgr 手动/半自动切换
- 读写分离：应用层路由或 Pgpool-II 自动分流

### 4.2 日常运维要点

#### 4.2.1 备份策略
| 类型 | 工具 | 频率 | 保留 | 存储位置 |
|------|------|------|------|----------|
| 逻辑全量备份 | pg_dumpall + pg_dump -Fc | 每日 02:30 | 7 天 | 本地 + 对象存储 |
| 物理基础备份 | pg_basebackup -Ft -z | 每周日 | 4 周 | 对象存储 |
| WAL 归档 | archive_command -> S3 | 实时 | 30 天 | 对象存储 |
| 逻辑周备 | pg_dump --schema-only | 每周日 | 30 天 | 对象存储 |

#### 4.2.2 WAL 归档配置
```ini
# postgresql.conf 关键参数
wal_level = replica
archive_mode = on
archive_command = 'rclone copy %p s3://db-backup/postgresql/wal/%f'
max_wal_senders = 5
wal_keep_size = 1024    # MB，保留足够 WAL 供备库追赶
```

#### 4.2.3 备份脚本逻辑（scripts/postgresql_backup.sh）
1. `pg_dumpall --globals-only` 导出角色、表空间等全局对象
2. 遍历数据库执行 `pg_dump -Fc -Z6`（custom 格式，自带压缩）
3. 可选 `pg_basebackup -Ft -z` 物理全量备份（`BACKUP_MODE=physical`）
4. 上传 S3 + rclone check 校验 + 清理过期备份
5. 推送 textfile 指标供 node_exporter 采集

#### 4.2.4 VACUUM 与 Autovacuum 治理
- 确保 `autovacuum = on`，定期监控 `pg_stat_user_tables` 死元组
- 大表设置独立 `autovacuum_vacuum_scale_factor`（如 0.05）
- 高写入表定期手动 `VACUUM ANALYZE`，避免事务 ID 回卷（XID wraparound）
- 监控 `n_dead_tup` 与 `last_autovacuum`，及时干预

#### 4.2.5 关键参数基线
| 参数 | 推荐值 | 说明 |
|------|--------|------|
| shared_buffers | 物理内存 25% | 缓冲池 |
| effective_cache_size | 物理内存 75% | 查询规划器估算 |
| work_mem | 16~64MB | 排序/哈希内存 |
| maintenance_work_mem | 256MB~1GB | VACUUM/CREATE INDEX |
| max_connections | 100~200 | 配合连接池使用 |
| wal_buffers | 16MB | WAL 缓冲 |
| checkpoint_completion_target | 0.9 | 平滑 checkpoint |
| random_page_cost | 1.1（SSD） | 优化随机读成本估算 |
| log_min_duration_statement | 1000 | 记录 >1s 慢查询 |
| autovacuum | on | 自动清理死元组 |

### 4.3 PostgreSQL 告警规则
| 告警 | 条件 | 级别 |
|------|------|------|
| 实例宕机 | pg_up == 0 | Critical |
| 流复制延迟 | pg_wal_lsn_diff > 1GB | Major |
| 连接数过高 | activity_count / max_connections > 0.8 | Major |
| 事务回滚率高 | rollback / (commit+rollback) > 10% | Minor |
| idle in transaction | count(state='idle in transaction') > 10 | Major |
| 缓冲池命中率低 | blks_hit / (blks_hit+blks_read) < 95% | Minor |
| 死锁 | increase(deadlocks[5m]) > 0 | Minor |
| 临时文件过大 | increase(temp_bytes[5m]) > 1GB | Minor |

> 完整规则文件见 `configs/rules/postgresql.yml`，采集目标见 `configs/targets/postgresql.yml`。
> postgres_exporter 默认端口 **9187**，推荐使用 `prometheuscommunity/postgres_exporter`。

## 五、数据库统一运维规范

### 5.1 变更窗口
- **常规变更**：周三 22:00~24:00（业务低峰）
- **重大变更**：周六 00:00~04:00
- **紧急变更**：需 SRE leader 审批，全程双人在场

### 5.2 变更流程（SOP）
1. 变更前：备份 + 评估影响 + 通知相关方
2. 变更中：小步执行，每步验证，保留回滚点
3. 变更后：观察 30 分钟，确认无异常

### 5.3 高危操作拦截
通过 Ansible Playbook 封装高危操作，禁止直连执行：
```bash
# 禁止操作清单（需审批）
- DROP DATABASE / TRUNCATE
- DELETE FROM 不带 WHERE
- FLUSHALL / FLUSHDB (Redis)
- rm -rf / var/log/* (系统)
```

### 5.4 数据库账号管理
| 账号类型 | 权限 | 使用场景 |
|----------|------|----------|
| 应用账号 | 指定库 RW | 业务连接 |
| 只读账号 | 指定库 SELECT | 报表/BI |
| 运维账号 | SUPERUSER + REPLICATION | 运维操作 |
| 监控账号 | pg_monitor / pg_read_all_stats | exporter |
