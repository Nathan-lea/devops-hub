# 告警与应急方案

## 一、告警体系设计

### 1.1 告警分级
| 级别 | 含义 | 响应时效 | 通知方式 | 示例 |
|------|------|----------|----------|------|
| **P0/Critical** | 核心业务中断 | 5 分钟 | 电话+短信+IM | MySQL 宕机、K8s API 不可用 |
| **P1/Major** | 影响业务功能 | 15 分钟 | 短信+IM | 主从延迟、磁盘 > 90% |
| **P2/Minor** | 潜在风险 | 1 小时 | IM | CPU 高、慢查询增多 |
| **P3/Warning** | 信息通知 | 工作时间 | IM | 证书 30 天到期、备份完成 |

### 1.2 告警路由与收敛
```
┌─────────────┐
│ Prometheus  │
│ Alert Rules │
└──────┬──────┘
       │
┌──────▼──────┐     分组/抑制/静默      ┌───────────────┐
│Alertmanager │ ─────────────────────> │ 企微/钉钉/飞书  │
└──────┬──────┘                        │ 短信/电话      │
       │                               └───────────────┘
       ▼
   值班轮换（PagerDuty/oncall）
```

### 1.3 Alertmanager 配置要点
详见 `configs/alertmanager.yml`，核心策略：
- **分组（group_by）**：按 alertname + host 分组，避免刷屏
- **抑制（inhibit_rules）**：主机宕机时抑制该主机上的其他告警
- **静默（silence）**：维护窗口预先静默
- **路由（route）**：按 severity 和 team 分流

## 二、核心告警规则集

### 2.1 主机层告警
| 告警名 | 条件 | 级别 |
|--------|------|------|
| 主机宕机 | up == 0 for 1m | Critical |
| CPU 高 | 100 - avg(rate(cpu[5m])) > 90 for 5m | Major |
| 内存高 | (1 - mem_available/mem_total) > 90 for 5m | Major |
| 磁盘空间 | disk_free/disk_total < 0.15 for 5m | Major |
| 磁盘空间 | disk_free/disk_total < 0.05 for 1m | Critical |
| 磁盘 IO 高 | iowait > 30 for 5m | Minor |
| 系统负载 | load5 > cpu_cores*2 for 10m | Major |
| 文件句柄 | fd_used/fd_max > 80% | Minor |
| 时钟偏移 | abs(clock_skew) > 1s | Major |

### 2.2 网络层告警
| 告警名 | 条件 | 级别 |
|--------|------|------|
| 端口不可达 | probe_success == 0 for 1m | Critical |
| HTTP 5xx | http_5xx_rate > 1% for 2m | Major |
| 证书过期 | ssl_expiry < 30d | Warning |
| DNS 解析失败 | probe_success == 0 | Major |
| TCP 延迟高 | probe_duration > 1s for 5m | Minor |

### 2.3 数据库告警
（详见 04-数据库运维方案 中的告警表）

### 2.4 K8s 告警
| 假警名 | 条件 | 级别 |
|--------|------|------|
| 节点 NotReady | kube_node_status_condition != Ready for 3m | Critical |
| Pod CrashLoop | kube_pod_container_status_restarts > 5 for 5m | Major |

## 三、应急响应 SOP

### 3.1 告警处理流程
```
告警触发
   │
   ▼
确认告警（1分钟内 ACK）
   │
   ▼
评估影响 ──> 影响业务？──是──> 立即止损（优先恢复服务）
   │                │
   │                否
   │                ▼
   │            定位根因
   │                │
   ▼                ▼
记录处理过程      修复问题
   │                │
   ▼                ▼
更新值班日志 <─── 验证恢复
   │
   ▼
事后复盘（24小时内）
```

### 3.2 止损优先原则
**优先级：恢复服务 > 定位根因**
- 先回滚、重启、切换备用、扩容
- 保留现场（日志/快照）后再排查
- 故障恢复后再做根因分析

### 3.3 常见故障应急预案

#### 3.3.1 主机宕机
```
1. 确认主机是否真宕机（ping + console）
2. 确认影响范围（哪些服务受影响）
3. 措施：
   - 虚拟机：云控制台重启
   - 物理机：IPMI/远程管理卡重启
   - K8s：确认 Pod 已重调度到其他节点
4. 恢复后：
   - 检查服务自启
   - 检查数据一致性
   - 确认监控恢复
5. 记录故障时间线
```

#### 3.3.2 MySQL 主库故障
```
1. 确认主库状态（是否能连接）
2. 评估是否需要切换：
   - 主库无法快速恢复 -> 提升从库
3. 切换流程：
   a. 确认从库数据同步完成（Seconds_Behind_Master=0）
   b. 停止从库 IO 线程
   c. 等待 relay log 应用完
   d. 提升从库为主（reset slave all; set global read_only=0）
   e. 更新 ProxySQL/应用指向新主库
   f. 旧主库恢复后作为新从库接入
4. 通知研发验证
5. 全程记录
```

#### 3.3.3 K8s 集群 API 不可用
```
1. 确认 apiserver 进程状态
2. 检查 etcd 集群健康
3. 检查证书是否过期
4. 措施：
   - apiserver 崩溃：重启 kube-apiserver
   - etcd 损坏：从快照恢复
   - 证书过期：续期证书
5. 验证 kubectl 可用
6. 检查所有组件状态
```

#### 3.3.4 磁盘满
```
1. 确认磁盘占用（df -h, du -sh /*）
2. 定位大文件/目录
3. 紧急清理：
   - 日志：truncate 或清理旧日志
   - 临时文件：清理 /tmp, /var/tmp
   - 容器：docker/crictl rmi --prune
   - MySQL binlog：PURGE BINARY LOGS
4. 根本解决：
   - 扩容磁盘
   - 调整日志保留策略
   - 配置告警提前预警
```

#### 3.3.5 DDoS / 流量突增
```
1. 确认流量来源（netstat, ss）
2. 云环境：启用 DDoS 防护 / 高防 IP
3. 措施：
   - 封禁恶意 IP
   - 限流/熔断
   - 临时扩容
4. 保留抓包数据供分析
```

## 四、值班机制

### 4.1 值班排班
- **主值班**：7×24 轮班，负责一线响应
- **备值班**：主值班升级时的二线支持
- **专家值班**：按领域（DBA/网络/安全）三线支持

### 4.2 值班交接
- 每日 09:00 交接
- 交接内容：未关闭工单、待处理事项、特殊配置变更
- 交接记录存档

### 4.3 升级机制
```
告警 → 主值班（5min 未 ACK）→ 备值班（15min）→ 专家值班（30min）→ 领导
```

## 五、事后复盘（Postmortem）

### 5.1 复盘模板
```
故障标题：____
故障时间：____ ~ ____（持续 ____ 分钟）
故障等级：P0/P1/P2
影响范围：____
故障原因：____
时间线：
  HH:MM  发现告警
  HH:MM  确认影响
  HH:MM  执行止损
  HH:MM  恢复服务
  HH:MM  确认恢复

根因分析（5Why）：
  1. 为什么发生？
  2. 为什么没被预防？
  3. 为什么没快速发现？
  4. 为什么没快速恢复？
  5. 为什么会扩散？

改进项（Action Items）：
  - [ ] 短期（1周内）：____ 负责人：____
  - [ ] 中期（1月内）：____ 负责人：____
  - [ ] 长期（季度）：____ 负责人：____

经验教训：____
```

### 5.2 复盘原则
- **对事不对人**：聚焦系统和流程，不追责个人
- **无指责文化**：鼓励坦诚分享
- **可执行改进**：每个改进项必须有负责人和 deadline
- **闭环跟踪**：改进项进度定期 review

## 九、安全事件应急 SOP（详见 11-入侵检测与网络安全方案）

### 9.1 概述
网络安全攻击的检测与响应详见 **[11-入侵检测与网络安全方案](11-入侵检测与网络安全方案.md)**。
本节补充安全事件相关的告警与应急流程。

### 9.2 安全告警规则
详见 `configs/rules/security.yml`，覆盖以下类别：
| 告警组 | 内容 |
|--------|------|
| Wazuh HIDS 告警 | 严重安全事件、文件完整性变更、rootkit检测、sudo异常 |
| Suricata NIDS 告警 | 网络攻击、端口扫描、反向Shell、挖矿连接、DNS隧道、数据外泄 |
| 暴力破解告警 | SSH/Nginx/MySQL/Redis 爆破检测与封禁统计 |
| 异常连接告警 | 非白名单出站、新增监听端口、非常规端口、威胁情报命中 |
| 容器安全告警 | 容器内Shell、特权容器、K8s API访问、敏感目录挂载 |
| 审计告警 | 密码文件修改、sudoers变更、SSH配置变更、cron任务变更 |

### 9.3 安全事件分级与响应
| 事件级别 | 类型 | 响应时效 | 响应动作 |
|----------|------|----------|----------|
| P0 | 确认入侵/数据泄露/勒索 | 5 分钟 | 隔离主机 + 通知管理层 + 取证 |
| P0 | 反向Shell/rootkit | 5 分钟 | 隔离主机 + 进程取证 + 排查 |
| P1 | 暴力破解成功/端口扫描 | 15 分钟 | 自动封禁 + 检查入侵痕迹 |
| P1 | 异常出站连接 | 15 分钟 | 阻断连接 + 排查进程 |
| P2 | 可疑行为/新增端口 | 1 小时 | 记录 + 分析趋势 |

### 9.4 安全事件响应流程
```
安全告警触发
   │
   ▼
确认与分类（5分钟内）
   │
   ├─ P0（入侵/勒索/反向Shell）
   │    ├─ 立即隔离主机（host_isolate.sh）
   │    ├─ 阻断攻击源（防火墙封禁）
   │    ├─ 通知安全负责人 + 管理层
   │    ├─ 取证（内存dump + 磁盘快照 + 日志保全）
   │    └─ 清除威胁 + 从备份恢复
   │
   ├─ P1（暴力破解/端口扫描/异常连接）
   │    ├─ 自动封禁（fail2ban / Wazuh主动响应）
   │    ├─ 人工确认是否成功入侵
   │    └─ 加固 + 记录
   │
   └─ P2（可疑行为）
        └─ 记录 + 分析趋势 + 定期回顾
```

### 9.5 安全事件后复盘
安全事件复盘除遵循第五节通用复盘模板外，还需额外记录：
- 攻击入口（漏洞/弱密码/配置缺陷）
- 攻击者行为时间线
- 影响范围（哪些主机/数据被波及）
- 检测是否及时（从攻击发生到告警触发的延迟）
- 防护改进项（漏洞修复/规则优化/基线更新）
